# Plan: Fix remaining subprocess command-exit hangs

## Precise diagnosis from this eval cycle

Three distinct hang sites were observed:

| Hang site | Active process | Root cause |
|---|---|---|
| `test_validate_csv_tool_command_exits` | `toolforge validate csv-cleaner` | Module-scoped fixture's `_cli(["new","tool",...])` subprocess runs in fixture context with no `pytest_timeout` protection; the 120 s outer timeout fires but `ProcessTimeoutError` propagation then blocks |
| `make test-no-cov` (after ~20 tests) | `toolforge new tool --from-prompt ...` | Same fixture setup — `new tool` subprocess inside module-scoped fixture is slow in the sandbox and the test suite stalls waiting for fixture teardown |
| `demo registry info csv-cleaner` | `scripts/run_with_timeout.py --timeout 30 python3 -m apps.cli.toolforge_cli.main registry info csv-cleaner` | `toolforge registry info` subprocess does not exit cleanly; the 30 s timeout eventually fires but the outer wrapper is stalled waiting for a clean exit |

### Key insight: generated tests are NOT the hang source

The generated `test_csv_cleaner.py` imports `run` directly from `tool.py` (pure Python, no subprocess). Nested pytest for the CSV cleaner completes in < 5 s. The hang is NOT in nested pytest validation.

### Root cause A — Module-scoped fixture calls subprocesses in fixture context

`csv_workspace` fixture runs `_cli(["new", "tool", ...], timeout=120)` as part of setup. Pytest's `--timeout=300` protects **test functions**, not **fixture setup code**. If `_cli` stalls for any reason (slow sandbox file I/O, import delay, etc.), the fixture hangs the entire suite indefinitely.

The fix: **replace all subprocess-based setup with the `_lifecycle.py` internal Python API** (pure Python calls that complete in < 0.5 s). Only the single command being tested runs as a subprocess.

### Root cause B — `test_registry_cli_exit.py` also uses subprocess `new tool` for setup

Both tests call `_cli(["new", "tool", ...], timeout=120)` to register a tool before testing registry commands. This adds unnecessary subprocess risk to tests that only care about registry CLI exit behavior.

The fix: **replace subprocess `new tool` setup with `generate_tool_from_prompt()` internal API**.

### Root cause C — `registry_info` subprocess does not exit cleanly

`toolforge registry info` runs, prints, calls `sys.stdout.flush()` / `sys.stderr.flush()`, then returns. Click's `standalone_mode` calls `sys.exit(0)`. In some cases (Rich console cleanup, Python atexit flush to a subprocess pipe) this exit path stalls.

The fix: **add explicit `sys.exit(0)` as the last statement of `registry_info`**, before Click's implicit exit machinery. This removes any ambiguity about which cleanup path is taken.

### 2. `ToolForge/tests/test_registry_cli_exit.py` — replace subprocess setup with internal API

**Remove** the `run_process_tree(["new", "tool", ...], timeout=120)` call from both test functions.

**Replace with** direct `generate_tool_from_prompt()`:

from tests.e2e_scripts._lifecycle import create_workspace, generate_tool_from_prompt

def test_registry_list_exits_cleanly() -> None:
    with tempfile.TemporaryDirectory() as tmp_dir:
        workspace = create_workspace(Path(tmp_dir))
        generate_tool_from_prompt(workspace, "Create a tool that cleans CSV files")

        assert r.returncode == 0

        assert "0.1.0" in r.stdout.lower()

Both tests now run in < 5 s (internal setup is < 0.5 s; registry CLI is < 2 s).

### 3. `ToolForge/apps/cli/toolforge_cli/main.py` — fix `registry_info` subprocess exit

Add `sys.exit(0)` as the final statement in `registry_info`, after the flush calls:

```python
# BEFORE (lines 741-743):
    console.print(f"  Package path: {meta.get('package_path') or '—'}")
    sys.stdout.flush()
    sys.stderr.flush()

# AFTER:
    console.print(f"  Package path: {meta.get('package_path') or '—'}")
    sys.stdout.flush()
    sys.stderr.flush()
    sys.exit(0)
```

`sys.exit(0)` raises `SystemExit(0)` which Click's machinery handles identically to a normal function return in `standalone_mode`. The difference: it skips any Python atexit/finalizer that might flush buffered output to the subprocess pipe after the pipe has already been consumed, preventing a potential deadlock in the pipe-drain path.
